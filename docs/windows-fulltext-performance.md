# Windows 正文搜索：COM 优化与验证

> 本文记录 2026-10-22 在单台 Windows 电脑、固定候选页上的测试，不是所有环境的性能保证。文中 `.runtime/optimization/` 下的日志、源码快照和原始测量文件仅保存在测试电脑，不随仓库发布；本机邮箱缓存和服务状态也不上传。安装与接入请看 [Agent 安装指南](agent-install-guide.md)。

## 实现

本次改动基于 v0.3.0 `d321a5f`。优化 Windows COM 路径及其索引写入方式，不改变分页上限、查询语义或离线文件后端的读取协议。

原实现对同一页的每封邮件、多次读取过程都遍历同一文件夹的祖先链；元数据、邮件版本和位置也通过许多单独的 COM 调用取得。优化后：

- 每个操作开始时确认请求目录属于当前存储的 Inbox/Sent 子树，排除 Deleted；每封邮件仍检查当前父目录和存储标识。操作结束再次检查完整祖先链，防止整个目录或祖先目录在扫描期间被移动。
- 每个检查阶段只遍历一次祖先链，同时供允许目录和 Deleted 判断使用；结束阶段重新遍历，不复用先前的归属结论。遇到已取得身份的同一个存储根对象时，复用其标识并终止，不再重复读取根的 EntryID/StoreID。循环或超过 128 层的目录链拒绝搜索。
- 用一次 `PropertyAccessor.GetProperties` 批量读取版本号、父目录、存储标识；候选扫描同时批量获取主题、接收时间、消息标志、大小和原始发件人字段。每项值先检查类型，HRESULT、缺失或不支持的属性使用原对象模型回退。该 API 的单项错误行为参见 [Microsoft GetProperties 文档](https://learn.microsoft.com/en-us/office/vba/api/outlook.propertyaccessor.getproperties)。
- 原始接收时间按 UTC 解读，再转换为与原对象模型一致的时间；未读标志按 MAPI 的 READ 位解释。参见 [接收时间定义](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidtagmessagedeliverytime-canonical-property) 和 [消息标志定义](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidtagmessageflags-canonical-property)。
- 独立正文读取及索引更新仍在读取前后比较版本及下载状态。直接扫描把中间的正文后检查合并到最终全部候选校验：候选元数据保留读取前的原始版本，最终来源校验核对同一个版本；不能用中途的新版本替换原始版本。未通过最终校验的正文标记为 `unverified`，结果不能发布。省去与原始状态自身的重复比较，但仍要求可用的强版本或完整备用校验信息。独立调用候选接口仍保留立即校验，弱版本正文不作跨请求复用。
- Exchange SMTP 地址仍通过原解析路径取得；附件数量只为实际返回的命中邮件读取，并在读取后做最终版本校验。候选邮件 ID 同时通过批量属性取得，不可用时回退原对象模型。没有跨请求复用邮件元数据，也没有用缓存替代最后的来源校验。
- Exchange 发件人解析在同次调用中只读取一次 AddressEntryUserType，保留普通用户、远程用户、通讯组和 SMTP 属性回退路径。
- Windows COM 默认恢复自动策略：没有数据库时首次直接扫描，最终校验成功后暂存一页具有可靠版本的完整正文，最多 30 秒；下一次查询才建立索引，已存在数据库时直接使用增量索引。暂存版本与新候选不符、过期或缺失时重新读取，不启动后台建库。复用本次扫描的邮件对象、PropertyAccessor 和读取元数据之前的版本；最终重新打开全部候选，校验原始版本、父目录、存储、下载状态和目录祖先链。每次仍最多 50 封、128 MiB，正文单封最多 1,600 万 UTF-16 单元。
- 显式 `com_body_mode=direct` 模式在查询为 ASCII、正文属于保守允许字符范围且没有字面命中时省去整段正文传输，返回绑定查询和版本的 `unverified_no_match`。允许范围含 ASCII、Latin-1 补充、部分标点、CJK 和全角字符；测试逐一确认其中非 ASCII 字符经 JS 小写转换不会产生 ASCII。因此 ASCII 真命中必由原正文的 ASCII 字符组成，OrdinalIgnoreCase 的负匹配不会遗漏它。土耳其大写带点 I、Kelvin 符号、希腊字母及其他未允许字符均回到原路径；所有命中仍传完整正文，使用原 JS 字面匹配和摘要函数确认。省去的原始正文仍计入字节预算，最终校验覆盖这些未命中邮件，普通索引写入器拒绝这种状态。
- 显式 `com_body_mode=indexed` 使用私有 SQLite 路径，首次就建立当前页索引；`auto` 或省略参数按需建立。自动策略首轮保留完整正文，不启用负匹配传输省略，以便第二次查询换词时也能建立完整索引。权限与数据库准备可同候选扫描重叠，准备成功后才写入；后续只读取缓存未命中的正文，最终来源校验照常覆盖全部候选。该选项只转发给 COM，不改变离线或 Mac 后端。超时、字节预算耗尽、缺失或变化保持明确状态。
- 工作进程分别缓存标识符的编码和解码结果，每个最多 256 个、使用大小写敏感的键；编码键包含 kind、EntryID 和 StoreID，减少重复 JSON/Base64 编码。最终校验仍重新打开每封邮件，缓存不包含 COM 对象、版本或目录归属。批量属性不可用时，备用 change key 查询复用同次操作已经取得的 PropertyAccessor，避免再获取一次。
- 通过当前 Store 的 `GetRootFolder()` 确定祖先遍历的终点，避免继续向非文件夹的 Parent 查询 EntryID/StoreID，首次调用时这会触发昂贵的 COM 属性解析。仍从请求目录逐层检查 Deleted 和 Inbox/Sent 归属；不支持根目录 API 的存储继续走原遍历。参见 [Microsoft GetRootFolder 文档](https://learn.microsoft.com/en-us/office/vba/api/outlook.store.getrootfolder)。边界只在本次操作内使用，不跨请求缓存文件夹归属。
- 批量正文到齐后，SQLite 使用一个事务写入本批可接受的版本；FTS 使用一次 INSERT SELECT 写入本批文档，减少逐封进入全文索引写入器的开销。文档和 FTS 同事务提交，FTS 失败也整体回滚。等待 COM 期间不持有 SQLite 写锁。原逐封加载协议继续用于离线后端和没有声明批量能力的适配器。

每封邮件的父目录标识与存储标识需要同时匹配，不能只比较父目录 EntryID。属性定义见 [ParentEntryId](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidtagparententryid-canonical-property) 和 [StoreEntryId](https://learn.microsoft.com/en-us/office/client-developer/outlook/mapi/pidtagstoreentryid-canonical-property)。不同表示形式或不可用的二进制属性保留对象模型校验。

## 正确性验证

合成 COM 对象测试分别运行批量路径与兼容路径，覆盖：

- 元数据读取时版本号改变、版本号消失、邮件移动。
- 正文读取时版本改变、邮件移入其他目录或 Deleted。
- 请求目录整体移动，及祖先目录移动但邮件直接父目录 ID 未变。
- 最后校验期间目录移动；下载可用性改变但 change key 未变。
- 其他存储具有相同父目录 EntryID 的情况。
- 单项属性 HRESULT、整次批量调用不可用、备用版本信息缺失、仅有邮件头、正文缺失或超长。
- UTC 时间转换、未读标志、SMTP 地址和元数据字段回退。
- 批量版本不符、重复或缺失 ID、备用版本不可持久复用、字节预算和超时、事务回滚，以及只补齐实际返回结果的附件数量但仍校验所有候选的分页行为。

完整 Node 测试集：**90 项通过、0 项失败、16 项因 Windows 不适用的 POSIX/macOS 条件跳过**。保留既有 COM 目录/版本/下载状态、分页、并发、SQLite 安全路径与事务测试。新增默认首轮扫描、次轮建库、未命中正文换词复用、暂存版本失效/过期/关闭释放、校验失败不暂存、显式直接扫描及索引切换、直接模式不访问不可用数据库路径、选项只路由至 COM、未命中压缩结果的查询/版本绑定与原始字节预算、禁止将该结果写入 SQLite。测试扫描全部 Unicode 码点，核对工作进程实际允许字符范围的 JS 小写映射；合成 COM 覆盖中文、Latin-1、标点、大小写、带点 I/Kelvin 回退、时间/字节上限和读取期间的版本/位置/下载状态变化。标识符编码缓存检查 kind/StoreID 隔离、结果一致、容量界限和每次仍重新打开邮件。使用项目内测试临时目录，没有修改系统环境设置。最终日志：`.runtime/optimization/restore-hybrid-tests.log`。

真实邮箱性能测试还逐次核对结果顺序、邮件 ID、主题、发件人、接收时间、未读状态、大小、附件数量、下载状态、扫描量和 next_offset。正文读取场景核对整个分页正文对象。遇到不完整正文、待重试状态或结果不一致，基准脚本失败，不将该场景作为有效加速数据。

这些检查保留了实时邮箱的变更检测能力；接口仍然是 live-offset 分页，不是邮箱事务快照。检测到变更会返回错误或要求重试，不能保证外部 Outlook 在校验结束之后仍不发生变化。

## 测量方法

测试日期为 2026-10-22，Windows，Node.js v24.19.0，同一运行中的经典 Outlook 会话。第一、二轮历史测试对比：

1. `legacy`：原始 v0.2.1，`2c8636e`。
2. `baseline`：未经优化的 v0.3.0，`d321a5f`。
3. `current`：相应轮次的最终实现，工作进程源码 SHA-256 保存在原始数据中。

延续前次基准：固定收件箱及 `before=2026-10-22T04:24:53.709Z`；搜索统一 `scan_limit=50`、`limit=200`。该页 50 个项目中有 49 封邮件。三个工作进程均先预热；每个常规场景预热后测 7 轮，轮换并反转三个版本的顺序，取中位数。原基准首次建索引使用全新独立目录，只测一次，不作显著性判断；第三轮增加每轮全新进程和索引的七轮补充测量。

计时包括各自参数校验、桥接、PowerShell、COM 与索引处理；不包括 CLI 启动、HTTP 或 MCP 传输。测试过程中不并行运行其他测试或基准。结果仅代表该固定候选页和本机环境，不能外推为所有邮箱大小、查询类型或机器的固定倍数。

计算：耗时下降率 = `(baseline - current) / baseline × 100%`；速度倍数 = `baseline / current`。负下降率表示变慢。不能把索引首次建立与已有索引的查询混为同一个指标。

## 第八轮：默认直接扫描，索引显式可选（历史记录）

基线为第七轮快照 `.runtime/optimization/before-default-direct`，工作进程 SHA-256 为 `cd2d91502c1ce8509bc4a5eb425321cef618c96f278b5260340d202819d0728a`。默认每次直接扫描，已有数据库也不参与搜索；`--com-body-mode indexed` / `com_body_mode: "indexed"` 显式启用索引，首次立即建库。省略该参数或传 `direct` 切回扫描。没有后台任务、后移建库或 30 秒正文暂存。人员筛选、命中摘要、分页、下载状态与最终来源校验均保留；其他后端不改变。

## 为什么此前比 v0.2.1 慢

v0.2.1 先读取候选元数据，匹配主题和发件人；这些字段未命中时才读取正文做字符串匹配，达到返回数量上限就停止。v0.3.0 的持久化正文索引增加了候选版本和目录检查、缓存查找或写入、以及返回前的来源校验；它仍需扫描同一个实时候选窗口，SQLite 不能替代这部分 COM 读取。首次建库还需准备私有目录、数据库和 FTS 数据，而 v0.2.1 不承担这些成本；当前默认策略的首轮直接扫描同样不承担建库成本，但保留新版的准确性校验和摘要。

原始 v0.3.0 又在每封正文的独立 RPC 中重复解析相同目录、遍历祖先链，并逐封提交索引。本次将这些工作按批次合并。热查询则保留原始候选版本，把重复的中途校验合并到最后，并只为实际返回的结果读取附件数量。

对这里的 50 项小窗口，旧版从 Outlook 已缓存邮件中直接读取正文并不昂贵，因此索引省下的正文读取时间很容易被 COM 校验抵消。这不是 SQLite 查询本身变慢。也不能简单把所有来源检查替换成 Outlook Table 批量读取：例如必要的 `DownloadState` 并不支持作为 Table 列，仍需从邮件对象读取，参见 [Microsoft 不支持的 Table 属性说明](https://learn.microsoft.com/en-us/office/vba/outlook/how-to/search-and-filter/unsupported-properties-in-a-table-object-or-table-filter)。
